`recent_reviewer_rationales` records prior scheduling explanations. Use this advisory history to avoid repeating an unchanged investigation; check current dependencies, reservations and evidence before reusing a conclusion.

Fill available worker slots with useful tasks. Edit scopes must be disjoint. A `lean_closure` task may work on a dependency of another active task; an ordinary task may not. This includes transitive semantic and Lean/definition dependencies. Tasks may share unchanged dependencies. Each task keeps its slot through checking and cleanup. There is no worker backlog. `available_heavy_slots`, when present, limits profiles marked `lightweight: false`. Otherwise `available_sol_slots` limits Sol profiles. Use eligible profiles outside the capped class for other slots; each profile's task restrictions still apply. Limits may change while you work; dispatch uses the current limits.

Return `{"assignments": [...], "reason": "..."}`. Each assignment contains `id`, `profile`, `compiler` (`managed` or `none`), `task_kind` (`ordinary` or `lean_closure`), optional `timeout_seconds`, and `review`, an ordinary reviewer response using the contract below. New node names must start with the assignment's displayed prefix. The assignment number in that prefix is its position in `assignments`, starting at 1; the assignment `id` remains a label. Use `compiler: "none"` for work confined to assigned TeX files; Lean inspection is allowed, but compilation and edits to other files are unavailable.

For ordinary Modeling with model preservation enabled, an assignment using `compiler: "managed"` may include `evidence_paths`: a list of exact files under `reference/model-evidence/` to create or edit. List new files as well as existing files; comments and node prefixes do not authorize evidence paths. Ordinary acceptance still checks all edits and evidence claims.

For a verifier request, audit, phase advance, or other ordinary reviewer action, return `{"assignments": [], "action": {...}}` with that ordinary response. Required verifiers also run automatically.

`deferred_verification_advisory` in the dispatch context and structured request lists native verification subjects waiting on prerequisite verification, including subjects that have no queued verifier job yet. It is scheduling advice, not an actionable blocker list: these summaries are not blocker IDs and cannot be placed in task, reset or override action buckets. They do not by themselves prohibit work on the listed node or goal. `verifier_jobs` shows created jobs, not every future obligation; an empty `corr_verify_nodes` on a Review request is not a correspondence-clear signal. Base-legal next-active candidates are routing choices, not a guarantee that ordinary worker admission is ready. Consider the relevant nodes and coarse goal when planning work: native preparation projects that goal and runs the ordinary transition, which may require verification before a worker. This does not bar unrelated admissible goals or compatible `lean_closure` work. Recheck the latest job outcomes and native batch receipts; do not repeatedly submit an unchanged assignment rejected for a still-pending verifier requirement. Global changes wait for current tasks to finish and retain their existing approval gates.

The ordinary response schema below applies to each assignment's `review` or the envelope's `action`.

For ordinary proof assignments with `coarse_goals`, omit `stuck_math_audit` even when the run-wide audit contract below is active. Native preparation projects the selected goal without the run-wide audit latch. Put useful advisory notes or exact scratch-file paths in `review.comments`. Ordinary actions and `lean_closure` assignments retain their displayed audit-report contract.

Modeling assignments use ordinary tasks and run exclusively. Wait for current tasks to finish before submitting any exclusive assignment alone.

Node retirement is worker work: put `dispatch_node_retirement: true` in an ordinary managed assignment's `review`, not `action`. The pending retirement order survives coarse-goal projection. Choose a permitted active coarse goal; a completed current anchor cannot be reused. Include the retired nodes and consumers to repair in the authorized scope; consumers still require ordinary cone and prerequisite checks.

A `lean_closure` assignment may edit one existing node's Lean proof body and add imports to use existing lemmas. Do not forbid import additions in the assignment. These tasks cannot plan, decompose, alter statements or write NL proofs, regardless of the selected model. Closure tasks may run while verifier lanes are pending; they do not clear those verification requirements. For these assignments, `lean_closure_candidates` replaces the ordinary next-active and coarse-anchor routing rules below; leave `next_active_coarse` empty. The list includes eligible SKETCH nodes and nodes outside the current coarse focus. When the configured costs differ greatly, inexpensive closure attempts can save NL proof writing and review. In theorem-stating, the objective remains clearing verifier blockers and advancing phase; closing every Lean proof is not required.

Make use of available parallelism. Use spare worker slots for compatible Lean closure attempts on promising existing nodes, including sketches. Look beyond the immediate task for eligible nodes. Use `profile_token_cost_comparison` to compare the configured lightweight and heavyweight profiles at the displayed fixed token mix. Frequent lower-cost closure attempts can be economical with occasional successes; account for compiler time and slot occupancy when choosing useful work. When `lightweight_attempts_per_node` is set, profiles marked `lightweight: true` share that per-node launch budget; `lightweight_attempts_by_node` shows launches already used, including failed attempts and automatic retries. At the limit, choose an eligible non-lightweight profile or another node. Audit priorities do not require leaving spare slots idle when useful compatible closure work is available.

Use `closure_attempts_by_node` for closure history by frozen provider/model, including older tasks, native outcomes, active statuses and unlaunched reservations. Each launched task counts once; separate native retries count separately, and correction/transport turns stay within their task. Launch bookkeeping can precede provider startup. For a complete node lookup, read `.parallel_dispatch.closure_attempts_by_node["NodeId"]` in `{{structured_request_path}}`; recent task IDs identify retained evidence.

Keep total worker slots fully utilized whenever a compatible eligible node has no recorded closure attempt. Start with `closure_candidates_without_recorded_launches`, check current reservations and dependencies, and assign an eligible lightweight profile for an exploratory closure attempt. Choose another ready node when you have high confidence that the proposed node requires further decomposition before closure can succeed. Apply the current profile, per-node attempt, compiler and exclusive-work limits to each assignment. Explain any remaining capacity or decomposition constraint in the batch reason.

For `lean_closure`, use `compiler: "managed"`. In `review`, set `decision: "continue"`, `reset: "none"`, `next_active` to the existing node, an allowed `next_mode` of `local` or `targeted`, `allow_new_obligations: false`, `must_close_active: true`, and `authorized_node_ids: []`. Leave difficulty updates, semantic edits, and reviewer-wide actions empty. These closure limits apply in theorem-stating too, in place of the ordinary authoring defaults below.

Worker timeouts cover execution through candidate submission. Host acceptance and publication do not expire submitted work. Use the displayed profile defaults unless the task warrants a different permitted limit. Review completed attempts, including failures and automatic retries, before assigning related work. Return `{"assignments": [], "reason": "..."}` when no useful work is currently available.

When `worker_handoffs` lists saved files, its `path` is readable in this checkout. These files are advisory, not accepted source. To pass one to a worker, name that path in the assignment's `review.comments`; the worker must stay within its new scope and recheck any reused work.

Use the supplied checker tools for Lean work. If a compiler command is blocked, follow its diagnostic; do not work around the guard.
